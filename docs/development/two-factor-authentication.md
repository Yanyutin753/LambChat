# 双重验证（2FA）

双重验证默认关闭，由每个用户自愿选择。在「个人设置 → 个人资料」启用双重验证。输入当前密码，用支持 TOTP 的验证器 App 扫描二维码（也可以手动输入密钥），然后输入 6 位验证码确认。尚未确认的配对在 10 分钟后过期，不影响原有登录。仅使用第三方登录的账号，先通过「忘记密码」设置账号密码。

启用时显示 10 个一次性恢复码，请立即离线安全保存，不要发到聊天中。服务器只保存恢复码的带密钥哈希。恢复码丢失但仍持有验证器时，可输入密码和新的验证码重新生成；旧恢复码立即失效。关闭 2FA 也需要密码和验证码（或恢复码）。同时丢失验证器和全部恢复码时，不能通过密码找回解除 2FA。

密码登录和 Google、GitHub、Apple 登录均要求第二步验证。第一步通过后，5 分钟的随机挑战只允许完成第二步，不能访问 API、刷新令牌或连接 WebSocket。TOTP 使用 30 秒时间步，接受相邻一步的时钟偏差；已使用的时间步不能重放。刚启用时再次登录需要等待验证器生成下一验证码。

启用、关闭或重新生成恢复码会轮换账号登录版本，撤销旧访问令牌、刷新令牌及后续 WebSocket 握手；当前操作会获得新令牌。修改或找回密码同样撤销旧登录令牌并清除待确认配对，但保留已启用的 2FA。重置链接必须有有效期，提交时原子校验令牌、有效期、原密码和登录版本并消费令牌；并发提交只允许一次成功。已建立的通知 WebSocket 每 15 秒复核身份；两条聊天 SSE 接口每 15 秒在发送下一段数据前复核，JWT 到期也会终止输出。撤销存在最多一个复核周期的传播窗口；已经发出的数据无法收回，正在执行的后台任务和已经授权的有限文件下载不会因此取消。开启 2FA 或重新生成恢复码时，同一笔用户记录更新还会切换 PAT 凭据版本，使该账号所有旧 PAT（包括旧版本无版本字段的 PAT）及设备配对失效。旧设备必须重新完成登录和第二步验证再配对；现有沙箱连接在下一条指令或心跳前校验 PAT 并关闭，不能继续收取新指令。未开启 2FA 的账号不受强制配对要求影响。

## 运维与安全边界

- 必须使用 HTTPS；配对密钥和恢复码是敏感数据。二维码在客户端本地生成，无第三方二维码服务，浏览器不持久化这些数据。
- TOTP 密钥使用项目现有 Fernet 加密设施加密，依赖 `JWT_SECRET_KEY` 和 `MCP_ENCRYPTION_SALT`，恢复时须保留这两个配置。不要独立轮换后遗失旧密钥，否则已绑定的验证器将不可解密。
- Redis 保存 5 分钟挑战及限流计数，MongoDB 原子更新保证恢复码、TOTP 时间步只能消费一次。Redis 不可用时登录、配对和第二步验证拒绝继续，不会降级放行。多实例共享同一 Redis 和用户库，服务器保持时间同步。
- 每个 IP 每 5 分钟最多 30 次第一步/第二步请求；密码登录按输入的用户名/邮箱分别限每 5 分钟 10 次；第二步验证和管理操作按数据库账号 ID 分别限每 5 分钟 10 次，无法通过换登录别名或换挑战增加第二步额度。IP 限流依赖反向代理正确覆盖转发头，账号限流不依赖 IP。不存在“信任设备免验证”及邮箱关闭 2FA 的入口。
- 2FA 不防止已登录设备被控制、会话令牌被窃取或实时钓鱼。上线前需用测试账号验收密码/OAuth 登录、配对、恢复、退出与原生客户端；本地自动化结果不等于生产验收。

设计参考：[RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)、[OWASP MFA 指南](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)。

桌面端「换账号配对」支持填写验证码或恢复码，验证通过后才创建沙箱 PAT，整个过程不会切换聊天账号。daemon CLI `login` 仅在服务端要求 2FA 时隐藏输入验证码；协议对未启用 2FA 的旧服务端保持向后兼容。已有客户端需升级才能使用新增的二步登录界面。

LambChat Web、桌面端和移动端共用二步登录组件，daemon CLI 有二步配对支持；共享组件测试不能代替各原生客户端和验证器 App 的实际测试。验收须分别记录前后端自动化、浏览器连真实后端、真实 App 扫码和手机/桌面客户端。


## 2026-10-23 本地安全复核

本次补上密码重置令牌的原子消费和聊天 SSE 身份复核。浏览器连接实际 FastAPI 路由与认证中间件，使用隔离 MongoDB 和临时 Redis 数据库完成了：密码登录、待确认配对、错误码拒绝、二维码本地渲染、手动密钥配对、TOTP 登录及恢复码登录。验证码由独立 Node `crypto` 实现生成，没有调用后端 TOTP 函数，也没有实测上述手机验证器 App。

实际 HTTP 验收覆盖：旧访问/刷新令牌拒绝、挑战不能当访问令牌、恢复码不能重放、daemon CLI 必须完成第二步后才能获得沙箱 PAT、PAT 不能管理 2FA。找回密码使用实际路由，仅邮件发送传输替换为本地捕获：10 个并发重置请求恰好 1 个成功；重置后 2FA 保留，旧登录挑战及令牌失效，已建立 WebSocket 被定期复核断开，新密码仍需第二步验证。

测试账号、数据库、Redis 键和临时凭据已清理。未执行外部 OAuth 授权、真实邮件投递、验证器 App 扫码、原生客户端真机及生产部署；这些不列为通过。后续补充验证：开启 2FA 和重新生成恢复码会原子撤销旧 PAT/设备配对；关闭 2FA 不会恢复历史失效凭据。


PAT 使用独立的 `pat_version`，只在上述两种操作成功时切换；失败验证、打开配对页面、取消操作及关闭 2FA 不会切换，也不会重新激活历史 PAT。创建 PAT 时还检查发起请求的登录版本：即便旧 JWT 已通过请求入口验证，随后发生 2FA 变更，也不能用旧身份取得新版本 PAT。先读取旧版本再插入的并发 PAT 会立即失效，不依赖跨集合批量删除成功。其他账号的凭据不受影响。PAT 有效性检查每次读取账号当前版本，不使用跨请求权限缓存；该新增字段默认空，未发生上述操作的旧账号和旧 PAT 保持兼容，无需强制用户启用 2FA。

## 每次电脑配对的重新验证

2FA 仍默认关闭，由用户自主开启。开启后，所有新 PAT 签发（包括当前账号、空作用域、自动配对入口）都必须通过新的第二因素验证。有效 JWT 本身不能授权配对。当前账号在本地沙箱设置输入验证器码或恢复码；未开启 2FA 的账号保持原流程。

换账号及 CLI 的配对登录显式请求 `for_pairing`，成功验证后除登录凭据外返回一份 60 秒有效的 `pairing_token`，仅保留在当前操作内存。服务端按独立用途保存其哈希键，绑定用户及 `auth_version`，以 Redis GETDEL 原子消费。它只能兑换一次 PAT，不能代替登录 JWT，也不能跨账号、跨安全版本复用；普通登录不签发配对授权。验证码及恢复码继续遵循单次消费、限流和存储故障时拒绝的规则。

旧客户端对已开启 2FA 的账号创建新配对会被服务端拒绝，需更新客户端；未开启账号及现有有效设备连接不受此新验证步骤影响。启用 2FA / 重置恢复码导致的旧 PAT、设备配对失效规则不变。
