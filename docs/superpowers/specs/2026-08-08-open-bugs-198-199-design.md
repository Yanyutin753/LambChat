# Open Bugs #198 and #199 Completion Design

## Goal

Close the remaining concrete bug reports in the open issue list by completing
Tavily quota monitoring and alerting (#198), repairing and deploying the E2B
template workflow, and removing stale docx skill path assumptions (#199).

The work includes repository changes, regression tests, migration tooling, and
verification against the external services configured by the current checkout.

## Current State

- PR #202 already retries transient MCP stream failures and restores JSON array
  strings to arrays, so the first two failures in #198 are covered.
- Tavily plan exhaustion is currently only returned as an opaque MCP tool error.
  Tavily now provides an authenticated `GET https://api.tavily.com/usage`
  endpoint containing key and account usage/limit values. The endpoint itself is
  limited to 10 requests per 10 minutes.
- The E2B template definition includes `ripgrep` and `librsvg2-bin`, but
  `scripts/create_e2b_template.py` imports `Template` from the absent
  `e2b_code_interpreter` package. The installed E2B SDK exposes `Template` and
  `default_build_logger` from `e2b`.
- The configured MongoDB currently contains no `/home/oai/skills` or
  `validate.py` references in `skill_files`, `skill_marketplace_files`, or the
  legacy `system_skills` collection. A migration must still be safe to run on
  another deployment that retains those records.
- `/skills/` is virtual MongoDB-backed storage. Skill scripts must be copied to
  the session workspace with `transfer_file` or `transfer_path` before shell
  execution; replacing one obsolete absolute path with another is invalid.

## Scope

### In scope

1. Poll Tavily's official usage endpoint without exposing API keys.
2. Emit deduplicated warning and critical alerts before and at exhaustion.
3. Preserve MCP availability when usage monitoring is unavailable.
4. Make the E2B template build script executable with the installed SDK.
5. Provide an idempotent, dry-run-first migration for obsolete docx skill
   instructions.
6. Build and verify the configured E2B template, switch the current environment
   to the verified template, and restart only services that are already running.
7. Update and close #198 and #199 with test and live-verification evidence.

### Out of scope

- A generic billing framework for every MCP provider.
- A new monitoring UI or notification center redesign.
- Closing #158, which contains no defect reports, or implementing #203, which is
  an enhancement request already answered by the maintainers.
- Refactoring unrelated deepagents v0.7 migration work.

## Design

### 1. Tavily usage monitor

Add a focused provider module under `src/infra/mcp/` with three responsibilities:

1. Resolve a Tavily credential only from a trusted source. Resolution precedence
   is `TAVILY_USAGE_API_KEY`, then the `tavilyApiKey` query parameter on the exact
   host `mcp.tavily.com`, then an Authorization bearer token on an HTTPS
   `*.tavily.com` host. Accepted credentials must use Tavily's `tvly-` prefix.
   `TAVILY_USAGE_PROJECT_ID`, when set, is sent as `X-Project-ID`; project scope
   is never inferred from an untrusted proxy URL. Raw credentials are never
   logged, returned, or used directly in cache keys.
2. Call the official usage endpoint with a short timeout and validate the
   returned key/account usage and limit fields.
3. Produce a sanitized snapshot containing server identity, plan name, separate
   quota buckets, overall severity, timestamp, and the last monitoring error.

The returned limits are not collapsed into one ambiguous ratio. Each positive
limit is evaluated independently:

- `key` uses `key.usage / key.limit` and is a hard limit;
- `account_plan` uses `account.plan_usage / account.plan_limit`; reaching the
  plan limit is exhausted only when PAYGO is unavailable, otherwise it remains
  a critical budget alert because requests may spill into PAYGO;
- `account_paygo` uses `account.paygo_usage / account.paygo_limit` when PAYGO is
  configured and is a hard limit.

Each bucket retains its own ratio and severity. The overall severity is the
maximum bucket severity, with hard-limit exhaustion outranking budget warnings.
An explicit provider response saying that the request exceeds its plan limit is
always recorded as exhausted even if the preceding cached snapshot was lower.

Monitoring is invoked after a Tavily tool call and after a detected Tavily plan
limit error. It is fail-open: monitoring exceptions are logged and swallowed, so
they never change the tool result or scheduled-task outcome.

### 2. Distributed rate limiting and alerts

Use Redis to coordinate refreshes across API and worker processes. A cache key
contains only a SHA-256 credential fingerprint and has a minimum ten-minute TTL.
This is a conservative polling interval below Tavily's allowance of 10 usage
requests per 10 minutes, leaving capacity for manual diagnostics. A short-lived
distributed lock prevents simultaneous refreshes on cache miss. An in-process
monotonic cache is the fallback when Redis is unavailable.

Thresholds are configurable with conservative defaults:

- warning: usage is at least 80% of the applicable limit;
- critical: usage is at least 95%;
- exhausted: usage is at least 100% or Tavily returns its plan-limit error.

Crossing a threshold emits a structured warning/error log once per severity and
billing window. Repeated calls at the same severity do not spam logs. Falling
below a threshold resets the alert state for the next billing cycle.

The latest sanitized snapshot remains in the distributed cache for log
correlation and tests. No new public or administrator API is added without an
identified operational consumer.

### 3. MCP integration

`MCPClientManager` associates the resolved Tavily monitor context with wrappers
for Tavily tools only. `MCPToolWithRetry` retains its current retry and argument
normalization behavior, then asks the monitor for a cached or due refresh.

Plan exhaustion is classified separately from retryable transport failures. It
is not retried, is surfaced to the agent with an actionable quota message, and
forces a monitor refresh when the provider rate limit permits.

### 4. E2B template build and verification

Repair `scripts/create_e2b_template.py` to use the installed `e2b` SDK API. Keep
the existing package lists, but separate template construction from the external
build call so unit tests can verify the system packages and build parameters
without contacting E2B.

After tests pass, build a uniquely tagged candidate under the `lambchat-prod`
template name. Do not move the production tag during build. Record the prior
`E2B_TEMPLATE` value, and create one temporary sandbox from the candidate's
immutable build identifier before changing `.env`. Run:

- `command -v rg`;
- `command -v rsvg-convert`;
- a lightweight SVG conversion smoke test.

Always terminate the diagnostic sandbox in `finally`. If candidate verification
fails, retain the previously configured template and do not restart services.
If it succeeds, pin `E2B_TEMPLATE` to the SDK-returned immutable reference in the
form `lambchat-prod:<build_id>`, restart only previously running backend/worker
services, and run health checks. Only after health succeeds may the candidate
receive the `production` tag.

If post-restart health fails, restore the saved `E2B_TEMPLATE`, restart the same
service set again, verify recovery, and leave the production tag unchanged. The
failed candidate remains unpromoted for diagnostics and cannot affect newly
created production sandboxes.

### 5. Legacy docx skill migration

Add a bounded, idempotent migration command that scans `skill_files`,
`skill_marketplace_files`, and legacy `system_skills` for the exact path
`/home/oai/skills/docx/scripts/office/validate.py`.

The command is dry-run by default. The only automatically recognized source
shapes are main instruction documents: `skill_files` or
`skill_marketplace_files` records whose normalized `file_path` is `SKILL.md`,
and legacy `system_skills.content` records. The content must contain the exact
obsolete validation path. Matches in scripts, auxiliary files, missing path
metadata, or other fields are ambiguous.

For a recognized document, the migration inserts one canonical instruction
block before the first affected validation command:

1. call `transfer_path` for `/skills/docx/` into the current session workspace;
2. use the destination returned by `transfer_path` as the docx skill directory;
3. execute `scripts/office/validate.py` from that returned destination and never
   execute virtual `/skills/` paths directly.

It then replaces each exact obsolete executable path with the descriptive
placeholder `<transferred-docx-skill-dir>/scripts/office/validate.py`. The
canonical block has a stable marker so a second run cannot insert it twice.

Ambiguous records are reported without content or user identifiers and make the
command exit nonzero. They block apply and issue closure until manually corrected
and rechecked; they are not accepted exceptions.

Before each apply, the command writes an idempotent backup containing collection,
source document ID, original content, migrated content hash, migration ID, and a
30-day expiry to `skill_migration_backups`. The backup stays inside the same
MongoDB deployment and receives a TTL index. Each source update uses the original
content in the predicate (compare-and-swap), so concurrent edits are not
overwritten. Output contains collection and count information but no skill
contents or user identifiers. Re-running after success reports zero pending
changes.

A rollback mode restores the original content only when the current content hash
still equals the backed-up migrated hash; later user edits are reported and never
overwritten. Rollback is therefore available for 30 days without weakening the
compare-and-swap guarantee.

When the live dry-run finds zero matching records, no artificial production
write is made merely to exercise rollback. In that case, automated tests using a
temporary database/fake collection provide rollback verification, while the
zero-match dry-run is the live acceptance evidence.

The current configured database will be checked again immediately before apply.
If it still has zero matching records, the migration is considered complete
without writes.

### 6. Deployment and issue closure

External changes happen only after repository tests and lint pass. The rollout
sequence is:

1. Save the prior template setting, build a uniquely tagged candidate, and
   smoke-test its immutable build identifier.
2. Run the skill migration dry-run, then apply only recognized changes.
3. Update the current environment's `E2B_TEMPLATE` only after candidate
   verification.
4. Restart backend/worker processes only when they are found running and confirm
   health afterward; restore the saved value and restart again on failure.
5. Exercise a Tavily usage probe without printing credentials and confirm a
   sanitized snapshot is available.
6. Promote the verified build to the production tag only after health succeeds.
7. Post concise evidence to #198 and #199 and close them only when their code and
   operational acceptance criteria are satisfied.

## Error Handling and Security

- Provider credentials are redacted at every log and API boundary.
- Tavily monitoring has bounded timeouts and never blocks a tool failure path.
- Redis or Tavily outages degrade to a monitoring warning, not an MCP outage.
- Migration defaults to dry-run, creates expiring in-database backups, uses
  compare-and-swap, and blocks on ambiguous content.
- E2B verification cleans up temporary sandboxes even on exceptions.
- Existing user changes in the checkout are preserved and unrelated files are
  not reformatted or staged.

## Testing

The implementation follows red-green-refactor for each behavior:

- credential resolution accepts supported Tavily configurations and rejects
  unrelated/invalid credentials;
- usage parsing, ratios, thresholds, deduplication, Redis locking, and fallback;
- monitoring failures do not alter MCP tool results;
- plan exhaustion is non-retryable and triggers a permitted refresh;
- the E2B template builder imports from `e2b`, includes both required system
  packages, and passes the expected build options;
- migration dry-run, recognized rewrite, ambiguous-match blocking,
  compare-and-swap, backup/rollback, and idempotent second run.

Focused pytest suites and Ruff run before live operations. After deployment, the
temporary E2B sandbox and Tavily usage endpoint provide the live acceptance
checks.

## Acceptance Criteria

- Tavily transport and argument regressions remain green.
- A valid Tavily usage response produces a sanitized snapshot and appropriate
  threshold severity without exceeding the provider polling limit.
- Exhausted quota produces one actionable alert rather than repeated retries.
- `scripts/create_e2b_template.py` runs with declared project dependencies.
- A sandbox created from the selected production template contains working `rg`
  and `rsvg-convert` commands.
- No configured MongoDB skill record retains the obsolete path after migration;
  ambiguous records block completion until resolved, and rollback is verified.
- Existing services pass their health checks after the template/config rollout.
- #198 and #199 contain verification evidence and are closed; other open issues
  are left in their correct states.
