# 图片上传 UI 响应性优化设计

## 背景

当前聊天图片上传存在三类可见问题：

1. 图片解码、Canvas 缩放和多轮编码可能占用页面主线程，导致输入、滚动和点击短暂失去响应。
2. 每个 XHR 上传进度事件都会更新位于聊天页面上层的附件状态，触发聊天视图和虚拟消息列表反复重新渲染。
3. XHR 请求体发送完成后进度会到达 100%，但服务端仍需计算哈希、查重、写入对象存储和文件记录，界面因此显示“100% 仍在转圈”。

剪贴板图片还有独立兼容路径：部分应用只提供零字节文件占位符或内嵌 `data:image/...` 数据。现有零字节和远程图片拒绝规则必须保留。

## 目标

- 支持 Worker 的浏览器不再通过页面主线程压缩或解码大图片。
- 不支持 Worker 或 OffscreenCanvas 的浏览器仍可上传图片，不因能力检测失败而丢失功能。
- 显著降低上传期间附件进度引发的 React 状态更新次数。
- 区分图片准备、请求体上传和服务端处理，不再把 100% 请求体进度呈现为上传完成。
- 保持现有文件大小、数量、格式、权限、去重、取消和错误处理语义。

## 非目标

- 本次不迁移全部附件状态到新的全局 store。
- 不修改后端对象存储、文件记录或附件生命周期架构。
- 不增加第三方图片压缩依赖。
- 不改变服务端文件大小限制或图片质量目标。

## 方案

### 1. Worker 图片处理

新增专用图片处理 Worker，并保持 `compressImageFile(file, options)` 作为调用方接口。

Worker 负责：

- 使用 `createImageBitmap` 解码图片。
- 使用 `OffscreenCanvas` 缩放。
- PNG 编码一次；JPEG 按现有质量区间压缩，但使用有界搜索，避免无收益的重复编码。
- 返回压缩后的 Blob 元数据，主线程再构造 File，保留文件名和 MIME 类型。

主线程负责 Worker 生命周期、错误传播和降级选择。`compressImageFile` 的 options 增加可选 `AbortSignal`，每次操作结束后都必须终止 Worker，失败或取消时不得遗留后台任务。

### 2. 兼容性降级

按以下顺序选择处理方式：

1. 支持 `Worker + createImageBitmap + OffscreenCanvas`：在 Worker 中压缩。
2. Worker 图片能力不可用，但原图不超过当前上传限制：直接上传原图。
3. 原图超过上传限制：使用现有主线程 Canvas 压缩作为最后兼容兜底。

因此现代浏览器获得无阻塞路径；旧浏览器仍保持上传能力。只有“缺少 Worker 图片能力且原图超过限制”这一少数情况允许保留旧版短暂卡顿。

Worker 启动失败、运行时不支持 API 或编码失败，都必须进入同一降级流程，不得静默丢弃文件。

原图进入主线程兜底前仍需执行明确的硬上限检查，不能为了兼容性无界解码超大文件。最终产物必须重新执行现有角色上传限制校验；无法压缩到限制以内时使用现有“文件过大”反馈，不发送必然失败的请求。

### 3. 剪贴板内嵌图片

剪贴板分类仍同步完成，以便 Lexical 的粘贴命令立即决定是否消费事件：

- 非空原生 File：保持当前直接上传路径。
- 零字节原生文件：保持 `invalid-image`。
- 远程或无法读取的 `<img>`：保持 `invalid-image`，不得发起远程资源请求。
- 合法的内嵌 `data:image/png|jpeg|gif|webp;base64`：分类器只返回受支持的数据源，不在事件处理栈内同步解码。

实际解码优先交给 Worker。没有 Worker 时，通过本地 `data:` URL 的异步 Blob 转换降级；若浏览器也无法完成转换，则显示现有“重新复制或保存图片后上传”提示。任何降级都只处理已经通过 MIME 白名单验证的 `data:` URL。

### 4. 上传阶段状态

为临时附件增加可选阶段字段：

- `preparing`：图片压缩、剪贴板恢复或哈希准备中。
- `uploading`：XHR 正在发送请求体。
- `processing`：XHR 请求体已发送完，等待服务端响应。

上传中的可见百分比最高为 99%。收到 100% progress 事件时切换到 `processing`，显示本地化“服务器处理中”，只有成功响应后才移除上传状态并显示完成附件。

取消、失败和重试继续沿用现有附件卡片行为。所有新增用户文案同步更新中、英、日、韩、俄五个 locale。

### 5. 进度更新控制

进度通知需要同时满足：

- 忽略与上次相同的整数百分比。
- 高频事件最多每 100ms 提交一次附件状态更新。
- 阶段切换、完成、失败和取消立即刷新，不受节流延迟影响。
- 上传结束时清理待执行的计时器，不能在附件完成或组件卸载后写入旧进度。

本次保留 `pageDragAttachments` 的现有所有权，先通过减少更新次数获得主要收益，避免在同一变更中引入附件 store 重构风险。

## 数据流

1. 文件选择、拖放或粘贴产生 File/内嵌图片描述。
2. 前端完成大小、数量和剪贴板安全校验。
3. 创建 `preparing` 临时附件，让用户立即看到反馈。
4. Worker 压缩或兼容降级生成待上传 File。
5. Worker 计算 SHA-256，并调用现有 `/api/upload/check`。
6. 未命中去重时启动 XHR；节流更新 `uploading` 百分比。
7. 请求体到达 100% 后切换为 `processing`。
8. 服务端响应成功后替换为最终附件；失败则进入现有失败/移除逻辑。

若哈希 Worker 不可用或计算失败，前端跳过 `/api/upload/check` 并继续正常上传，不回退到可能阻塞页面的主线程全文件哈希。上传接口服务端仍会计算 SHA-256 并执行 owner-scoped 去重，因此这只失去一次客户端快速命中，不影响数据正确性。

## 错误与取消

- 图片 Worker 能力不足属于可降级条件，不显示错误 Toast。
- 图片数据损坏、剪贴板数据不可读时显示现有可执行提示。
- 用户取消时通过同一个临时附件任务控制器同时中止 XHR、终止关联 Worker、清除节流计时器并移除临时附件。
- 组件卸载时执行同样的资源清理，不产生卸载后的状态更新。
- 服务端错误继续使用现有错误解析和 i18n 映射。

## 测试策略

遵循红-绿-重构：

1. Worker 压缩测试：确认支持能力时不创建 DOM Canvas，并正确返回压缩 File。
2. 降级测试：确认无 Worker/OffscreenCanvas 时，小于限制的原图直接上传；超过限制时才调用主线程兜底。
3. 剪贴板测试：确认内嵌图片不在同步分类阶段解码，并覆盖无 Worker 的异步 Blob 降级。
4. 进度控制测试：确认重复百分比被忽略、高频更新被合并、100% 切换为 `processing`。
5. 生命周期测试：确认成功、失败、取消和卸载都会清理 Worker 与计时器。
6. 组件测试：确认附件卡片对三个阶段显示正确文案，成功前不显示完成状态。

完成相关测试后运行前端全量测试、ESLint、生产构建和 `git diff --check`。如果浏览器自动化环境可用，再补一次大图上传 Performance trace；该运行时测量不作为代码级测试通过的替代品。

## 验收标准

- 支持 Worker 图片能力的浏览器中，图片压缩和内嵌 Base64 解码不执行主线程 Canvas/字节转换。
- 普通图片在不支持 Worker 时仍可上传。
- 同一整数进度不会重复触发附件状态更新，持续上传最多约每秒更新十次。
- 界面不会显示“100% + 转圈”；请求体发送后显示“服务器处理中”。
- 现有零字节剪贴板、远程图片、上传限制、取消和错误反馈测试继续通过。
- 前端全量测试、Lint 和生产构建通过，且不修改无关文件。
