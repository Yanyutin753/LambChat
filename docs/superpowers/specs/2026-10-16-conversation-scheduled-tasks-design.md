# 对话内定时任务设计

日期：2026-10-16

> 2026-10-17 更新：用户已确认改为独立任务执行、结果投递回原会话。任务使用独立隐藏会话与历史，不再共享原会话 checkpoint、运行状态或插话队列。原会话仅持久化 `scheduled:result`，内部指令使用 `scheduled:instruction`。下文关于在原会话执行、继承实时上下文及等待原会话空闲的旧设计均已被此决定取代。

## 用户目标与已确认范围

用户希望直接在聊天中安排稍后继续、定期巡检和持续跟进；触发时读取原对话最新上下文，把结果追加到原对话。新创建的聊天任务默认在当前对话继续，仍可显式选择每次新建独立对话。多个任务不能覆盖运行状态或互相打断，也不能打断用户正在进行的工作。

复用现有调度器、任务管理面板、聊天提交、事件持久化、权限校验及通知链路，不增加第二套调度系统。截图仅作为使用场景参考，不授权自动回复外部社区、合并 PR 或发布生产。

## Codex 参考与适用边界

核对来源：[OpenAI Scheduled tasks](https://learn.chatgpt.com/docs/automations?surface=app)，2026-10-16。

官方区分独立任务和对话内任务：前者每次从保存的提示开始并新建聊天，后者回到已有聊天并使用其上下文；任务提示应明确每次的工作、何时报告以及停止或请求人工输入的条件。

官方文档没有公开同会话调度锁、用户输入竞争、内部 checkpoint 或去重实现。下述并发与恢复设计是针对 LambChat 的方案，不声称复制 Codex 内部实现。

## 当前代码事实

- `src/infra/scheduler/runner.py` 每次生成 `sch_<task>_<run>`，重试再加后缀；`source_session_id` 当前只用于来源追踪。
- 执行器直接向任务管理器提交，写入隐藏任务会话标志，传入 `project_id=None`。这些行为不能应用到原聊天。
- `src/infra/goal_continuation.py` 已有重入正常聊天提交、加载会话配置及检查忙碌状态的模式。
- `src/infra/task/manager.py` 的 local/arq 两条提交路径都会写当前运行状态；单纯在 scheduler 中先读状态不能防止跨实例竞争。
- `SessionScheduledTasksButton` 已能查看来源会话关联任务；保留该入口和全局任务面板。

## 模式与兼容性

增加 `execution_mode: conversation | standalone`。增加明确的 `target_session_id`，与记录来源的 `source_session_id` 分开，避免把历史来源误解释为执行目标。

- 聊天工具创建：省略模式时默认 `conversation`，目标从可信运行上下文取得，不接受模型指定其他人的目标会话。
- 从已有聊天打开创建表单：默认 `conversation` 并显示目标聊天；可选择 `standalone`。
- 全局任务页没有聊天上下文时：默认 `standalone`；选择 `conversation` 必须选择当前用户可访问的目标聊天，不隐式创建空聊天。
- 旧数据库文档缺少模式时按 `standalone` 读取，旧任务不自动迁移。旧 API 客户端未传模式的创建请求保留独立行为；新的聊天入口显式传新默认。
- `conversation` 必须有目标，创建及修改均验证所有权；切换模式不得在任务仍有执行中或待执行记录时发生，先暂停并清理未开始的待执行项。
- 历史独立任务继续使用原有命名、会话列表、重试和交付行为。

字段同步覆盖 create/update/persisted/response、执行投影、工具参数和预览、API 客户端、前端类型、表单、任务卡片与详情。错误使用现有 `ErrorCode`/`AppError`，新增文案同步 zh/en/ja/ko/ru。

## 上下文与授权

对话模式使用同一 session/checkpoint，通过正常聊天授权提交路径追加一个新的 run；不复制聊天文本到另一个会话，也不从创建时冻结历史。

每次真正开始时加载最新会话，继承当前 Agent、模型选项、角色/团队、项目、工作区/沙箱绑定、时区、语言、技能和 MCP 选择以及工具禁用配置。复用正常提交的配置解析，不能直接复制 provider 密钥、内部解析缓存或历史权限快照。

对话模式表单不单独配置与会话冲突的模型/Agent/角色；需要独立配置的用户可选独立模式。任务附加的文件引用沿用现有上传权限和引用生命周期，不能将历史附件重复当作新上传或越权读取。

每次提交及 worker 实际执行时重新验证用户状态、chat 权限、目标所有权、模型与工具权限。目标删除或失去访问权时暂停任务并给出可定位错误；禁止退回新会话执行。工作区或设备不可用时沿用既有错误处理，不自动换机器或放宽权限。

禁止覆盖原聊天名称、项目、收藏、来源、隐藏标志、已有后台任务身份或持续目标身份。任务归属记录在 run/trace 层，通知从该 run 查归属，不能靠单一 session metadata 存放多个任务的身份。

定时唤醒不创建、替换或消耗现有持续目标的续跑额度；有 active/等待人工/待续跑的持续目标时延后，避免把巡检消息绑定为该目标的新用户输入。

上下文沿用正常聊天的压缩机制，不承诺无限长度历史逐字输入。验收需证明上次结果及用户后续补充能影响下一次执行。

## 调度、并发与恢复

以现有任务运行记录作为持久化待执行意图，不新增独立队列服务。

1. 到期先创建可去重的待执行记录，记录任务、目标、计划时间和稳定 run ID。跨实例用唯一触发身份保证同一调度槽只入队一次。
2. 同任务最多保留一个未开始的唤醒。等待期间重复到期合并，不产生补跑洪峰；执行中到期最多再保留一个待执行项。不同任务保持独立记录，按计划时间及稳定 ID 排序。
3. 同一会话只允许一个运行占用。原子准入必须覆盖正常用户提交、local/arq 提交、定时唤醒、HITL 恢复和持续目标续跑；复用已有持久化状态和带 token 的租约模式，避免仅用进程内锁或先查后写。
4. queued/pending/starting/running/waiting_human/cancelling/recovering、未消费用户队列和待处理 steer 均视为忙碌。调度不能覆盖 `current_run_id`，不能取消、steer 或自动确认已有运行。
5. 用户待发送消息优先于未开始的定时任务。定时任务已运行时，用户输入走现有 steer/排队交互；不要为调度功能新增强制中断。此时暂停某个定时任务仅阻止其后续唤醒，现有停止按钮仍用于停止当前运行。
6. 忙碌时保留待执行记录。由现有调度运行时注册一个有界扫描器，在会话释放及周期扫描后尝试派发；一次性任务也必须等到空闲后运行，不能因一次冲突丢失。
7. 待执行项在开始前重新读取任务状态与目标权限；暂停/删除使未开始项取消，恢复周期任务从下一计划开始，不重放暂停期间所有触发。
8. worker 启动时和写入状态时验证 run 所有权。占用有 TTL 与续租，失去所有权的旧 worker 不再追加事件或覆盖新运行状态。
9. 重启可恢复未开始记录；已有提交凭据或 trace 的记录只对账，不盲目再执行。无法判断副作用是否完成时标为需要检查，不自动重放。

对话模式不沿用独立模式的“换个 session 自动重试”。未提交成功可重试准入；提交成功后的执行失败保留原 run 并报告，用户可显式再次执行。外部副作用无法承诺 exactly-once，必须避免以自动重试制造已知重复。

不同会话保持现有用户级并发限制，不新增全平台单任务限制。

## 提示、结果和通知

每轮以可辨识的定时唤醒消息携带任务名、任务 ID、本轮计划时间和持久任务指令，追加到原会话。实时 SSE、工具过程、历史查询、刷新和断线重连必须能按 run 区分。

沿用现有任务 CRUD 工具，不合并工具或新增重复调度工具。更新创建说明及 HITL 预览，清晰说明“在此对话继续”或“每次新建对话”，不再统一宣称每次新会话。任务提示明确读取最新上下文、避免重复处理、报告条件和停止条件。

增加 `notification_policy: always | meaningful_changes`。聊天创建的周期巡检默认 `meaningful_changes`；独立任务与旧任务保持 `always`。用户可修改。

`meaningful_changes` 以模型本轮明确的无更新结论作为依据，而不是比较两段自然语言是否相同：任务提示约定仅在确实无进展且无需用户处理时输出单独的 `NO_UPDATE`。只有成功结束且最终正文严格为该标记、没有待确认或错误时才抑制完成提醒。状态同步、运行记录和用量照常保存；前端把这一结果显示为紧凑的“检查完成，无更新”，不展示协议字样。不得按工具结果中出现的同名字符串抑制通知。

失败、超时、等待人工确认和明确进展走现有通知机制，保留 run 级去重；不把“静默”解释为丢弃状态事件、隐藏故障或关闭用户手动聊天的通知。对有意义进展的判断由模型完成，不能承诺完全准确。

本期复用既有 pause/resume/delete；用户可在聊天中要求任务停止，Agent 使用现有暂停工具。禁止仅凭自然语言声称已停止却不更新持久任务状态。

## 界面与信息架构

复用当前会话任务入口和全局定时任务页，任务卡片显示执行方式、目标聊天、下次计划/等待状态及通知策略。原聊天继续留在正常聊天列表，不被任务执行改成隐藏会话。

对话任务详情按 run 展示执行记录，点击定位原聊天对应 run；独立任务保留现有生成会话列表。原聊天关联多个任务时，暂停/立即运行/取消操作必须作用于选中的任务 ID。

遵循 `DESIGN.md`、`PRODUCT.md`、共享 token 与控件；验证深浅色、窄屏、键盘、长标题、加载/空/错状态以及五语文案。没有任务的聊天也应有可发现的创建入口，不能受当前 `count === 0` 隐藏按钮约束。

## 验收与验证

先写定向失败测试，再实现；全部改动稳定后通过 `python3 scripts/run_validation.py` 串行验证，worker/job 固定为 1。锁占用退出 75 时停止验证并如实报告，不排队重试。

必须覆盖：

- 旧文档及旧客户端保持独立；聊天新任务默认原会话，显式独立可用；缺少目标、他人目标、失效目标被拒绝。
- 连续两轮使用同一 checkpoint，第二轮读到第一轮结果和中间用户补充；项目、工作区、工具限制和原聊天属性不丢失。
- 同会话双任务同时触发、双实例争抢、触发与用户提交交织、local/arq 两条路径均不能同时取得运行所有权。
- waiting_human、用户队列、steer、持续目标活动时延后；空闲后运行，一次性任务不丢失，多个周期触发有界合并。
- 暂停/删除与准入竞争、worker 过期、重启、提交后失败和不确定状态不会盲目重复副作用或取消其他任务。
- 成功无更新仅抑制该 run 的完成提醒；失败、待确认、普通聊天仍通知；多任务通知归属及未读数正确。
- 会话入口无任务时能创建，表单可切换模式，运行记录能定位原聊天，独立任务列表保持可用。

执行真实服务集成验证：同一会话创建两个短周期任务，注入用户补充并制造 busy/HITL；确认串行、历史、通知与重启恢复。若环境不足，明确区分定向测试通过与真实链路尚未验证。前端完成后串行运行相关测试、lint/build，并进行浅色/深色/窄屏视觉走查。

## 非目标和已知边界

不新增 GitHub/Discord 连接器、事件触发调度、跨会话共享工作区互斥、自动发布、自动 worktree 或无限上下文存储。不同聊天指向同一工作区时仍可能文件竞争，沿用现有沙箱和工作区规则；同会话串行不等于整个文件系统串行。

后端可定时唤醒不代表离线本地设备可执行；本地沙箱需要相应设备在线。权限审批仍走既有机制。长历史受模型窗口和摘要质量限制。
