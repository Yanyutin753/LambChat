# 历史对话检索与记忆来源引用设计

## 背景

LambChat 已具备两类相邻能力：

- 会话列表可以按当前用户过滤，并使用会话侧搜索索引匹配会话名称和用户消息。
- trace/event 存储可以按 `session_id` 读取一段会话的历史事件。

这些能力目前主要服务前端 API。Agent 没有受控的历史对话检索工具，现有会话搜索也只索引用户消息，无法定位命中的具体 `run_id`，长期记忆则不能指回产生该记忆的原始问答。

## 目标

1. 让 Agent 搜索当前账号的正常历史对话，并定位到具体 `session_id` 和 `run_id`。
2. 让 Agent 按需读取某一轮或某个会话的历史详情。
3. 搜索和详情只呈现用户消息与 AI 最终答复，不呈现 thinking、工具调用、工具返回或其他中间事件。
4. 让长期记忆保存结构化的历史来源引用，召回记忆后可继续展开原始问答。
5. 覆盖项目内会话和归档会话，排除隐藏后台会话与定时任务执行会话。
6. 在不增加每轮固定工具 schema 成本的前提下提供上述能力。

## 非目标

- 不把完整历史对话复制进长期记忆。
- 不为历史对话引入独立向量数据库或新的外部检索服务。
- 不索引或展示思考过程、工具参数、工具结果、附件正文和运行诊断事件。
- 不改变现有前端会话搜索、会话事件 API 或聊天界面的可见行为。
- 不允许管理员借系统工具跨用户检索；Agent 工具始终以当前认证用户为边界。

## 方案选择

采用每轮对话索引方案。每个完成的 trace/run 物化可搜索字段，并由两个延迟加载的内部系统工具提供检索和详情读取。

未采用只复用现有会话索引的方案，因为它只能定位 `session_id`，命中后仍需扫描整个会话，也不能给记忆提供精确的 `run_id` 引用。

暂不采用全历史向量检索。当前中英文关键词索引足以支持第一阶段需求，成本和运维复杂度明显更低。未来可以在每轮索引上增加向量字段，而不改变工具接口或记忆引用格式。

## 数据模型

### 每轮对话搜索字段

在 trace 文档上增加版本化的 `conversation_search` 子文档：

```json
{
  "version": 1,
  "user_text": "本轮用户消息的规范化文本",
  "assistant_final_text": "本轮 AI 最终答复的规范化文本",
  "user_terms": ["..."],
  "assistant_terms": ["..."],
  "terms": ["..."],
  "indexed_at": "..."
}
```

trace 已有的 `user_id`、`session_id`、`run_id`、状态和时间字段继续作为身份、过滤与排序字段。为查询建立 `user_id + conversation_search.terms + completed_at` 复合索引。

搜索词从本轮用户消息和最终答复的完整可用文本生成；保存的规范化文本采用明确的字符上限，仅用于结果预览。详情读取仍以原始 trace/event 为事实来源，因此预览裁剪不会裁剪可读取的历史详情。

只有已结束且存在用户消息或最终答复的 run 才建立索引。运行中的当前 run 不参与搜索。失败或取消的 run 只有在存在已完成的最终答复时才可进入索引。

### 记忆来源引用

原生记忆文档增加：

```json
{
  "source_refs": [
    {
      "session_id": "...",
      "run_id": "..."
    }
  ]
}
```

`source_refs` 最多保存 20 个引用，按最近有效来源保留并按 `(session_id, run_id)` 去重。更新已有记忆和记忆压缩/合并时合并来源引用，而不是覆盖原引用。

来源引用不进入常驻 `<memory_index>`，避免增加固定 prompt 成本并延续隐藏内部记忆索引 ID 的约束。`memory_recall` 按需返回经过校验的 `source_refs`。

## 系统工具

### `search_conversation_history`

输入：

- `query`：必填搜索文本。
- `limit`：默认 10，上限 20。
- `cursor`：可选的不透明分页游标。

返回：

- 命中列表，每项包含 `session_id`、`run_id`、会话名称、完成时间、用户消息预览、最终答复预览和命中来源。
- `next_cursor`，用于稳定地继续读取更旧结果。

结果按相关性优先、完成时间次优排序。搜索候选以 `user_id` 和搜索词在 trace 上查询，再分批校验对应 session，直到填满当前页或候选耗尽。分页游标基于稳定排序键生成，不接受模型直接构造 Mongo 查询。

### `get_conversation_detail`

输入：

- `session_id`：必填。
- `run_id`：可选；提供时只读取指定 run。
- `limit`：未提供 `run_id` 时的分页大小，默认 10，上限 20。
- `cursor`：未提供 `run_id` 时的会话内分页游标。

返回：

- 会话基本信息。
- 按时间顺序排列的轮次，每轮只包含 `run_id`、时间、用户消息与 AI 最终答复。
- 会话分页使用的 `next_cursor`。

最终答复按现有流式事件语义归并 `message:chunk`；新 run 优先使用完成路径保存的最终输出，旧 run 回退到兼容事件读取与归并逻辑。中间事件不会进入返回结果。

### 工具暴露

两个工具加入 `lambchat_internal`，默认属于 deferred system tools，通过 `search_tools` 发现。只有显式策略把工具设置为 `inline_exposure=true` 时才直接暴露 schema。

工具从 `ToolRuntime` 获取当前用户身份，`user_id` 不出现在模型可填写的参数中。

## 记忆集成

`memory_retain` 增加可选的结构化 `source_refs` 参数。Agent 从历史搜索结果创建或更新记忆时，可以把命中的来源引用一并保存；当前聊天的自动记忆捕获则由运行路径传入当前 `session_id/run_id`，无需模型猜测。

所有来源引用在写入前必须验证：

1. session 属于当前用户。
2. session 不是隐藏后台会话。
3. session 不是定时任务执行会话。
4. run 属于该 session，且已经结束。

`memory_recall` 返回记忆内容时批量重新验证来源引用。已删除、已隐藏、已改变所有者或不再匹配的引用不会返回，但记忆正文仍保留。调用详情工具时再次执行同样的所有权和可见性校验，不能把记忆中的引用当作授权凭据。

## 数据流

### 新 run

1. Agent 完成一轮执行并得到最终 `output_text`。
2. trace/event 完成状态持久化。
3. 对话索引服务接收本轮用户文本、最终输出和 trace 身份，计算搜索字段并幂等更新 trace。
4. 索引失败只记录稳定错误类别并进入可重试回填范围，不阻塞最终答复交付。
5. 如启用自动记忆捕获，捕获任务携带本轮 `session_id/run_id`；只有真正写入或更新记忆时才保存引用。

### 搜索与展开

1. Agent 通过 `search_tools` 发现 `search_conversation_history`。
2. 搜索工具查询当前用户的 run 索引并过滤不可见 session。
3. Agent 从结果获取 `session_id/run_id`。
4. Agent 调用 `get_conversation_detail` 读取原始最终问答。

### 记忆召回与追溯

1. `memory_recall` 返回相关记忆及有效 `source_refs`。
2. 仅当当前任务需要核对原始上下文时，Agent 才调用 `get_conversation_detail`。
3. 详情工具重新授权并返回对应最终问答。

## 历史回填

新增版本化、幂等的后台回填任务，扫描缺失当前 `conversation_search.version` 的已结束 traces：

1. 分批读取 trace 身份与兼容事件。
2. 提取本轮用户消息。
3. 归并主输出的 `message:chunk` 得到最终答复。
4. 写入每轮搜索字段和版本号。
5. 保存进度并继续下一批。

回填具有批大小、并发数和单轮文本长度限制，可重复运行。单条坏数据被分类记录并跳过，不中断整批；下一轮仍可重试未成功写入版本号的记录。启动和回填不能阻塞聊天主路径。

旧记忆不强制生成来源引用，因为现有记忆正文无法可靠反推出唯一历史 run。只有新写入、被更新或明确从历史对话重新提炼的记忆获得引用。

## 权限与隐私

每次搜索、写入引用、召回引用和读取详情都执行服务端校验：

- `session.user_id` 必须等于当前认证用户 ID。
- `metadata.hidden_from_conversation_list` 不能为 `true`。
- `metadata.scheduled_task_id` 必须为空。
- 归档状态和项目归属不限制读取。
- `run_id` 必须属于传入的 `session_id`。

跨用户、隐藏、定时任务、已删除和不存在的 session/run 统一返回 `not_found`，避免泄漏资源是否存在。日志不记录消息正文、最终答复、记忆正文或完整来源引用列表。

## 边界与错误处理

- 空查询、过长查询、非法 limit 或损坏游标返回 `invalid_argument`。
- MongoDB 或事件存储暂时不可用时返回 `temporarily_unavailable`，不伪装成空结果。
- 搜索无命中返回成功的空列表。
- 详情页中的旧 run 若没有最终答复，返回用户消息和空的 `assistant_final`，不拼接 thinking 或工具事件补位。
- 文本、结果数量、引用数量、候选扫描量和并发读取量均设置硬上限，避免一次工具调用占满 Agent 上下文或数据库连接。
- 删除会话不要求同步重写所有记忆；召回和展开时的重新校验负责处理悬空引用。

## 测试策略

遵循红-绿-重构流程，覆盖以下层次：

### 索引与归并单元测试

- 中英文和混合文本能匹配用户消息及最终答复。
- 连续 `message:chunk` 只归并为最终答复，不包含 thinking、工具事件或推荐问题。
- 搜索文本预览裁剪不影响详情读取原始内容。
- 重复索引同一 run 是幂等操作。

### 工具与权限测试

- 搜索结果包含正确的 `session_id/run_id`，分页稳定且遵守上限。
- 详情可以读取单个 run，也可以分页读取整个 session。
- 项目会话和归档会话可见。
- 跨用户、隐藏会话、定时任务和 session/run 不匹配均不可见。
- 存储故障与无命中具有不同返回语义。
- 两个工具默认出现在 deferred internal tools，不增加直接工具列表。

### 记忆集成测试

- `memory_retain` 校验、保存、合并和限制来源引用。
- 记忆去重更新与压缩合并不会丢失仍有效的引用。
- `memory_recall` 返回有效引用并过滤悬空或越权引用。
- 自动记忆捕获能绑定当前 `session_id/run_id`，不依赖模型填写。
- `<memory_index>` 不暴露 `memory_id`、`session_id` 或 `run_id`。

### 回填与回归测试

- 旧 trace 可以从兼容事件结构回填。
- 回填断点恢复、重复执行和坏数据跳过行为正确。
- 现有前端会话搜索和会话事件读取行为保持不变。
- 内部工具 schema 预算测试继续通过。

## 验收标准

1. Agent 能通过关键词找到当前用户历史中某个具体 run，并拿到正确 `session_id/run_id`。
2. Agent 能根据引用读取该 run 的用户问题和 AI 最终答复，返回中没有中间推理或工具事件。
3. 记忆召回能返回可用来源引用，并可继续展开原始问答。
4. 项目和归档会话可检索，隐藏、定时任务和其他用户会话不可检索或展开。
5. 新 run 自动建索引；历史 run 可通过后台回填覆盖。
6. 工具默认延迟暴露，聊天主路径不因索引、回填或记忆来源处理而阻塞。
